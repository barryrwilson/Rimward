## Bugs found

### MEDIUM-1 — Nested `loadout` vs locked hangar row shape
Severity: MEDIUM (hangar record shape; not a locked HUD/BIO break)

shared-contract.md §1.2 (MERGE LAW) freezes each hangar hull as a flat row:
  scanner, miningLaser, concealedMounts, cargoCapacity, cargo, vitals.
Unknown keys are dropped.

shp-03-loadouts.md §3.1 / §3.3 persist a child object:
  hull.loadout = { v, miningLaser, scanner, concealedMounts, general, cargoCapacity }

If both notes land as written, shared-contract sanitize drops `loadout` on restore and first-slice equipment never sticks.

SHP-03 should bind the same fields the contract already lists on the row (plus allowlisted `general` if the contract is updated). Do not invent a nest that the merge-law drop-unknown-keys pass will strip.

### MEDIUM-2 — `hangar.mounted` / `instanceId` vs `mountedId` + `hulls[].id`
Severity: MEDIUM (same envelope)

shared-contract hangar:
  { mountedId, hulls: [{ id, ... }] }
  Mounted hull is a row in hulls.

SHP-03 migrate pseudo-code (§3.3):
  migrateWorldLoadoutOnce(ctx, hangar.mounted)
  for (const hull of hangar.hulls)

SHP-03 §3.1 also names `instanceId`. Contract and SHP-02 use `id`.

`hangar.mounted` is not a field. Implementers who write loadout onto a phantom mounted object will miss the persist row.

Correct migrate target: hulls.find(h => h.id === hangar.mountedId).

### MEDIUM-3 — First-slice PR3 drops WORLD_FIELDS mirrors; contract keeps them
Severity: MEDIUM (persist contract)

shared-contract §1.1 / §5: world.scanner / miningLaser / concealedMounts stay live mirrors of the mount. First implementation does not remove those keys.

SHP-03 §0.2, §3.2, Q6, PR3: after readers switch, drop the three keys from WORLD_FIELDS.

Write-through mirrors in PR1–PR2 match the contract. Dropping the keys is later-than-first-slice and conflicts with merge law until the owner edits shared-contract.
